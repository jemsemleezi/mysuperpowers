# 模块深化指南

如何在考虑依赖关系的前提下，安全地将一组浅模块深化为深模块。需先掌握 [LANGUAGE.md](LANGUAGE.md) 中的术语：**module**、**interface**、**seam**、**adapter**。

## 依赖分类

评估待深化的候选模块时，需对其依赖进行分类。依赖类别决定了深化后的模块如何跨 seam 进行测试。

### 1. 进程内依赖

纯计算、内存状态，无 I/O 操作。始终可深化——直接合并模块并通过新接口测试，无需 adapter。

### 2. 本地可替换依赖

存在本地测试替代品（如 Postgres 用 PGLite，文件系统用内存实现）的依赖。若替代品存在则可深化。深化后的模块使用替代品运行测试套件。seam 为内部 seam，模块外部接口无需端口（port）。

### 3. 远程但自有的依赖（端口与适配器模式）

跨网络边界的自有服务（微服务、内部 API）。在 seam 处定义 **port**（即接口）。深模块持有核心逻辑；传输层作为 **adapter** 注入。测试使用内存 adapter，生产环境使用 HTTP/gRPC/消息队列 adapter。

建议格式：*"在 seam 处定义 port，为生产环境实现 HTTP adapter，为测试实现内存 adapter，这样即使逻辑跨网络部署，也能集中在单一深模块中。"*

### 4. 完全外部依赖（需 Mock）

无法控制的第三方服务（如 Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的 port；测试时提供 mock adapter。

## Seam 使用规范

- **一个 adapter 意味着假设性 seam，两个 adapter 意味着真实 seam。** 除非确实有两个或以上 adapter 的合理性（通常为生产 + 测试），否则不要引入 port。仅含一个 adapter 的 seam 只是额外的间接层。
- **内部 seam 与外部 seam。** 深模块可以同时拥有内部 seam（仅实现内部可见，供自身测试使用）和接口处的外部 seam。不要仅仅因为测试需要就通过接口暴露内部 seam。

## 测试策略：替换而非叠加

- 一旦有了针对深化后模块接口的测试，原有的浅模块单元测试就失去了价值——请删除它们。
- 针对深化后模块的接口编写新测试。**接口即测试面**。
- 测试应通过接口断言可观察的结果，而非内部状态。
- 测试应能经受住内部重构——它们描述行为，而非实现。若实现变更导致测试必须修改，说明测试越过了接口边界。
